# 作法 — なぜこう測るのか

このリポは**ベンチマークではなく、ベンチマークを作る型とハーネス**。
問題（シナリオ）は外から `--scenarios` で渡す。ここに入っているのは測り方だけ。

世間のベンチと**作法は同じにする。問題だけを現場のものに差し替える**。
`MMLU 78.2` の代わりに「**要約は通らない。抽出なら3回中3回通る。1本1.3秒**」と言える状態を作る。

`examples/` に汎用4段（パブリックドメイン素材）が入っている。**そこが答える問いは1つだけ。**

---

## 0. ワンショットだけを測る。エージェントとして回せるかは測らない

**1プロンプト → 1出力**に閉じる。マルチターンもツール使用も入れない。

**理由: エージェントのベンチは、モデルよりプロンプトを測ってしまう。**
実測（2026-08-27）で、同じモデル・同じ仕事のまま、プロンプトに1文
（「手順が動かなくても自作スクリプトで代用するな。止まって報告しろ」）を足しただけで
**合否が反転した**。ハーネス・プロンプト・ツール構成という、測っていない変数が3つ増える。

「この仕事をこのモデルに任せられるか」は**別の問い**。そちらは
**本番の処理を副作用なしで一度走らせて、生成物が現行モデル版と同型かを見る**。
ベンチはそのスクリーニングにすぎない。

---

## 1. 同一条件で3回。3回とも通って初めて通過

- temperature は固定（既定 0）。プロンプトも固定。**変えるのはモデルと量子化だけ**
- 各シナリオを3回流し、**3回とも通ったときだけ通過**とする
- 「3回中2回」は**測定の失敗ではなくモデルの性質**。実務では使えない、が一目で分かる形で記録する
- temperature 0 でも実行ごとに揺れる。**揺れるかどうかを見るために3回回す**

**3回は「サンプル」ではなく「決定性の確認」。** `temperature 0 / seed 42` のローカルは
決定的なので、10回に増やしても同じ結果を10回見るだけで得るものがない。
1回にしないのは、**揺れていたときに気づけなくなる**から。3回は気づける最小の回数。

⚠️ **回数を増やすのは `N/3` が中途半端だった段だけ**（2026-08-27 決定）:

| 出た値 | 意味 | どうするか |
|---|---|---|
| `3/3` / `0/3` | 決定的に見える | **増やさない。**10回にしても同じ |
| `1/3` / `2/3` | **決定的でないことが確定した** | **その段だけ `--runs 10`**。たまたま外したのか、そもそも安定しないのかを分ける |

**増やす条件を結果のほうが教えてくれる**ので、最初から回数を上げておく必要はない。

⚠️ **クラウド（`anchor:`）だけは前提が違う。** CLI 経由なので `temperature` も `seed` も効かず、
**毎回変わる**。同じ `3/3` でも、ローカルは「決定的に通る」、クラウドは「3回引いて3回当たった」。
**強さの違う主張なので、並べて比べない。**

さらに合否が **全ケース × 全実行の AND** なので、**N を増やすほど落ちやすくなる**
（5ケース×3回 = 15試行の全勝が条件。1試行 95% のモデルでも全勝は 46%）。
**N は中立な設定値ではない。** 違う N の結果を並べるときは N を明記する。

確率にしない。`0.67` ではなく `2/3` と書く。

## 2. 条件を書かない結果は、後で比較できない

レポートの先頭に必ず全部書く（`lib/report.sh`）。埋まらない欄は省略せず `n/a` と書く。

model id / backend / digest / quantization / weight / temperature / seed / context 長 /
生成上限 / system prompt / 実行回数 / 日時 / ハード / **ベンチ版** / **ハーネスの commit SHA** /
**fixture 版** / **入力トークン数** / **切り詰めの有無** / 開始時のメモリ

入力トークン数と切り詰めを必ず残すのは、**入力が切れて壊れたのか、モデルが弱いのかを後から区別する**ため。

## 3. 階段で並べる。点数を出さない

シナリオは**要求の軽い順**に `001`, `002`, … と並べる。記録するのは
**通った段**と、**落ちた段の壊れ方**だけ。段の間に点数を挟まない。

⚠️ **落ちようのない段を一番下に置かない。** 誰でも通る段があると、全モデルが同じ顔で
「通過」と並び、**測っていないのに測った顔をした行**ができる。

## 4. 正解を持てるのは、答えが一意に決まる工程だけ

| | 正解の形 | モデルが正解を上回る危険 |
|---|---|---|
| **抽出**（答えが一意） | **完全な JSON**（`expected.json`） | **無い** |
| **要約・生成** | **持たない。**必須要素（`must-cover.txt`）＋失格条件 | **無い**（下限だけ決める） |

**要約に「正解の3行」を置くと必ず壊れる。** モデルがそれより良い要約を書いたときに落とすことになる。
**この失敗で1段を撤去した** — 指示文は「半日以内に試せるか」を聞き、正解ラベルは
「過去に実際にやったか」を表していた。別の質問だったので、**厳密に読むモデルほど落ちた**。

抽出の正解を作るときは、**測定値が1つだけの文**を使う。2つ入っている文だと、
モデルがどちらを選んでも正当なのに落ちる（`examples/002` の初版で実際にやった）。

- 失格条件は**機械判定できるものだけ**を判定に載せる。載らないものは `judge_undecidable` で人を呼ぶ

### 4b. 正解そのものを検品する

**未検品の正解で測った結果を、検品済みと同じ顔で並べない。** 落ちたのがモデルなのか
正解なのか区別できなくなる。`examples/REVIEW.md` が検品台帳。

### 4c. 判定は「落ちるべきものが落ちるか」と「落ちてはいけないものが通るか」を対で持つ

片方だけだと、**空振り**にも**過検出**にも気づけない。実際に踏んだ4種:

| 型 | どう空振り／過検出したか |
|---|---|
| 必須語だけ見る | 必要な語が入力に書いてあると、**入力を貼り返すだけで満点**になる → `judge_not_echo` |
| 末尾改行を落とす | `while read` は**末尾改行の無い最終行を捨てる**。モデル出力は必ずそうなので、1行の答えが素通り |
| 期待値を並べ書きする | 段を1つ足すだけでテストが落ちる。**何も守っていない** → 連続性を計算する |
| 語形で落とす | `centimeters` を `centimeter` と書いた答えで 0/3。**測っているのは値ではなく英語の語形** → 正規化 |

⚠️ **「なんとなく良くない」は機械では拾えない。** 文体は守れているが面白くない、は grep では出ない。
だから人を呼ぶ経路を必ず残す。ここを「機械が全部やります」と書くと、**静かに劣化する側に倒れる**。

## 5. ケースは実物から採る。合成しない。ただし fixture 化してから

- 合成したケースは「その問題が解けるか」しか測れない
- ⚠️ **実データをそのまま置かない。** `cases/FIXTURE.md` の方針で置換してから置く。
  **後から足すと作ったケースを作り直すことになる**
- 元データが再取得できないケースは**落とす**（埋めない）
- ⚠️ **ケースを外してよいのは、ケース側に特定できる欠陥があるときだけ。**
  「アンカーが落ちたから」を理由に外し始めると、**アンカーが通るまで問題を削る**ことになり、
  物差しが何も測らなくなる。外すときは**欠陥の中身を書き残す**（正解と入力が対応していない、
  閾値の上にケースが乗っている、等）。書けないなら外さない

この分離は構造で守っている。**`bench.sh` はシナリオの場所を知らない**（`--scenarios` で受け取る）。
`.gitignore` は忘れられるが、リポが別なら忘れようがない。

## 6. アンカーを必ず1本、ローカルより先に通す

いま実際にその仕事を回しているクラウドモデルを1本通す。役目は2つ。

1. 上限を知る
2. **安全弁** — アンカーが落ちたら、モデルではなく**問題設計が壊れている**

アンカーが全段通るまで、ローカルを測らない。**直すのは問題であって、判定を緩めることではない。**

アンカーが落ちたときに疑う順番:

1. **物差しを渡し忘れていないか** — 現場の仕事に付いている前提（判定基準・出力の形）を
   プロンプトから落としていないか。落としたまま測ると、モデルではなく問題設計を測る
2. **ケースが閾値の上に乗っていないか** — 正しくやっても境界に当たるケースは、モデルではなく運を測る
3. **正解と入力が対応しているか** — ラベルは正でも、その入力を見て人が判断したとは限らない
4. **判定が納品物以外に当たっていないか** — 後書き・自己申告に失格条件が当たると、
   本文が悪いように見える

ここまで潰してなお落ちるなら、それは**モデルの結果**として記録してよい。

⚠️ **コスト換算をアンカー価格で出さない。** アンカーが高いモデルだと**ローカルの割安さが
過大に出て判断を誤る**。換算は**その段を通す最安のクラウドモデル**の価格で出す。
「月100円ならクラウドでいい」と言える形にするのが目的。

## 7. 測る前に予測を書く

4対象 × 5段くらいの表を、**流す前に**書いて残す。**外れた予測がいちばん残る**。

## 8. 人を呼ぶのは境界が動いたときだけ

1. **初めてその段を超えたモデルが出た**（境界が動いた）
2. **判定が、事前に書いた予測と食い違った**
3. **判定器が「判断できない」と言った**

見てもらった結果は `disqualifiers.md` に1行追記され、次回から自動で効く。同じことを二度聞かない。

## 9. 版を切る — 3つのうち1つだけが過去を殺す

| 何をした | 過去の行はどうなるか |
|---|---|
| 新モデルを測った | 生きる（行が1本増えるだけ） |
| シナリオを足した | 生きる（その段が「未測定」になるだけ） |
| **手法を変えた**（回数・temperature・判定方法） | **全部、比較できなくなる** |

→ **手法を変えたら版を上げる。** カタログの行には測定時の版を書き、**版をまたいだ行を
同じ表で足し引きしない**。版はタグを手で書くだけでよい（自動追随の仕組みは持たない）。

**版の履歴:**

| 版 | 何を変えたか | 過去の行 |
|---|---|---|
| v1 | 最初 | — |
| **v2**（2026-08-26） | 005 に**分量の下限 600字**を追加（行数だけでは一文ずつ3行で通ってしまう）。非空行の数え方を `grep -c` から `awk NF` に、文字数を `wc -m` から locale 非依存の実装に | **v1 の行はそのまま有効。** どちらの変更でも 005 の判定は動かず、v1 で測った2件は再測定不要 |

### ⚠️ 数える道具は、環境で答えが変わるものを使わない

**同じ機械でも起動経路で数字が変わる**という形の事故を、この型は3回踏んでいる。

| 道具 | 何が起きるか |
|---|---|
| `grep -c` で非空行 | 末尾改行の無い最終行を数えるかが実装依存。この機械では `/usr/bin/grep` は数え、ログイン PATH 先頭の `ugrep` は数えない → **どのシェルから起動したかで行数が変わる** |
| `wc -m` で文字数 | **ロケール依存。** `LANG` 未設定（= cron・デタッチジョブ）ではバイト数に落ち、日本語が約3倍になる |
| 全角括弧を含む変数展開 | bash 3.2 の非 C ロケールで変数名に飲まれる（BB-368） |

→ **非空行は `awk NF`、文字数は python3。** 対話で決めた閾値が無人実行で別の意味になるのが、
この系統の怖さ。**閾値を決める前に、その数字がどの実装で出たのかを確かめる。**

### ⚠️ `disqualifiers.md` への追記は、実質「手法の変更」

境界で人を呼んで「これはダメ」と1行足す — これは運用の中で起きるのに、**判定基準の変更**である。
失格条件が1つ増えると、**過去に通ったモデルが遡って落ちる**可能性がある。にもかかわらず:

- カタログの行は前のまま「003 まで通過」と書いてある
- **テストは緑のまま**（落ちるのは過去の結果であって、いま走らせているものではない）
- **誰も気づかないまま、カタログが嘘になる**

→ 追記したら、**そのシナリオを過去に通ったモデルの行を再測定する**。
すぐ流し直せないときは行に再測定フラグを立て、**フラグの付いた行は「用途別の即答」の根拠に使わない**。

## 10. ホストを落とさない — 三段で守り、外れたら降りる

`weight × 1.3` は KV キャッシュ・context 長・ollama 本体・同時稼働プロセスを完全には表さない。
`inactive` も全量が確実に回収できるわけではない。だから1回の判定を信じない。

1. **起動前ゲート** — 降りるのは `usable × 2 < weight × 1.3`、つまり**望みが無いときだけ**。
   足りないが惜しい範囲（`usable < 必要量`）は**警告して流す**。報告に「押し込んで測定した」と残る
2. **ロード直後の再判定** — 重みが常駐した状態でメモリプレッシャーを見る。`critical` なら降りる
3. **実行中の監視（10秒間隔）** — メモリプレッシャー `critical` で即中止。**Jetsam を待たずに自分で降りる**

⚠️ **判定は「重み vs 総メモリ」ではなく「重み×1.3〜1.5 vs 実空き」**。総メモリと比べない。
⚠️ **止めるのは自分が起動したプロセスだけ。** 既に上がっているサーバは自分のものではない。

### ぎりぎりで降りない（R7 で変えた）

**`swap free` は見ない。** macOS の swap は固定領域ではなく、`dynamic_pager` がディスクの空きに
応じて増やす。`free = 961M` は「いま swapfile が何本あるか」であって残量の上限ではないので、
これをゲートにすると**詰まっていない機械を永久にブロックする**。

**実空き不足も、それ自体は降りる理由にならない。** `inactive` は要求されれば渡されるし、macOS は
圧縮してでも割り当てる。押し込んでスラッシングしたなら、それは失敗ではなく**測定結果**:

> mac01（10日稼働・実運用中）では 3B q8 は動くが、1本 ◯秒でスラッシングする → 実用外

**降りてしまうと、この行が永久に埋まらない。** ベンチの目的は肌感なので、ここを削らない。

降りる基準は「ホストが実際に苦しいか」に一本化する。その信号は派生値ではなく
**メモリプレッシャー**（Jetsam 自身が見ているもの）。

### スラッシングは合否ではなく、秒に付く条件

実行中の `swapin + swapout` の増分を記録し、報告に出す。0 なら秒はモデルの速度そのもの。
0 でなければ**その秒は「押し出しながら出した値」**であり、空いた機械なら速くなる。
カタログの行に秒を書くときは、増分が出た測定だと分かるようにする。

**測れないほうが、本番を落とすより安い。** ただし「測れなかった」と書けるのは、
**ホストが苦しくて降りたとき**だけ。狭かっただけのものを「測れなかった」に混ぜない。

## 11. 結果は貯めない。残すのは1行と、壊れ方の現物

モデルが変われば数字は意味を失う（既定モデルが黙って差し替わる例は実際にある）。
判定は1回の実行内で完結するので、**`results/` を持たない**。実行中の出力は scratchpad に置いて捨てる。

残すのは:

- **カタログに1行** — モデル / 量子化 / **実測の必要メモリ** / 通った段 / N回中何回 / 落ちた段の壊れ方 / 1本あたり秒数 / ベンチ版
- **落ちた段の壊れ方は、現物を1つだけ引用（2〜3行）**

⚠️ カタログの行に書く容量は**重みサイズではなく実測の必要メモリ**。`8B q4 / 5.0GB` と書くと、
次に読んだ人が「16GB なら余裕」と誤読する。

現物を残すのは、点数では絶対に伝わらないものがあるから。
「数字の読みが弱い」より「**16GB → 「ジービー」**」のほうが、半年後に読んで一瞬で伝わる。

## 12. 1適用あたり半日で収まる規模に抑える

5段・ケース5〜10件。**重い型は誰も使わない。** シナリオを足す手間が重くなった時点で、
このベンチは更新されなくなる。
