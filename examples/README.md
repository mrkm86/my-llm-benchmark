# examples — 素の能力を測る4段（汎用・公開可）

**このディレクトリが答える問いは1つだけ。**

> **このモデルは、1回のやりとりでどこまでできるか。**

アプリに埋め込む LLM エンドポイントとして使えるかを見るための段。
**エージェントとして回せるか（複数ステップ・ツール使用・自己修復）は測っていない。**

## なぜエージェント能力を測らないのか

**ハーネスとプロンプトを測ってしまうから。** 実測（2026-08-27）:
同じモデル・同じ仕事で、プロンプトに1文足しただけで合否が反転した。

| | 逃げ道あり | 「自作スクリプトで代用するな」を足した |
|---|---|---|
| 手順に従ったか | 自分でランナーを書いた | 従った |
| 生成物 | 前日の成果物を流用した壊れ物 | 正常 |

モデル間の比較にしたいのに、**測定値がこちらの書き方で動く**。だからこの4段は
すべて「1プロンプト → 1出力」に閉じている。

## 段

| 段 | 何を測るか | 正解 |
|---|---|---|
| `000-hello` | **配線。**モデルが呼べる / system が届く / 判定が効く | — |
| `001-extract-one` | **1件の構造化抽出。**JSON が壊れず、値が一致するか | **あり** |
| `002-extract-many` | **同じ抽出を3件。**1件も落とさないか | **あり** |
| `003-summarize` | **要約。**3行に畳めるか（日→日 / 英→日） | **持たない**（下記） |

## ⚠️ これは1本の階段ではない。軸が2本ある

```
抽出の軸   001（1件） → 002（3件）      ← ここだけが階段
要約の軸   003                          ← 別の能力
```

**`002` が ❌ でも `003` を測る意味がある。** 実測（granite4:micro）で
002 は通り 003 だけ落ちた。「連続して通った一番上の段」という読み方は、
**抽出の軸の中でだけ**成立する。

`001 → 002` の差は**難しさではなく件数**で、**同じ3つの事実を使っている**。
1件ずつ渡すか3件まとめて渡すかの違いだけなので、
**「やり切れるか」が単独で取り出せる**（実測で繰り返し出た「3件目が空になる／2件で打ち切る」を、
抽出能力と切り離して見られる）。

`000` だけ読み方が逆で、**❌ のほうが情報を持つ**（モデルではなく梱包を疑う合図）。

## 正解を持てる段と、持てない段

| | 正解の形 | モデルが正解を上回る危険 |
|---|---|---|
| 抽出（001 / 003） | **完全な JSON** | **無い** — 答えが一意 |
| 要約（002） | **持たない。**必須要素＋失格条件 | **無い** — 下限だけ決める |

**要約に「正解の3行」を置くと必ず壊れる。** モデルが正解より良い要約を書いたときに
落とすことになる。これは実際に一度やった失敗で、**そのために撤去した段がある**
（旧 `001-scout-filter`: 指示文と正解ラベルが別の質問を聞いていた。
厳密に読むモデルほど落ちる、という逆転が起きた）。

だから 002 は **上限を決めず下限だけ決める** — `must-cover.txt` に
「この要約に必ず残っていなければならない事実」を並べ、あとは失格条件で形を縛る。

| 素材 | 出どころ | 使う段 |

**実データ・社内データは1バイトも入っていない。** うちの仕事に固有の段は
別のところ（private 側）にあり、ここには来ない。

## 正解は未検品

**`REVIEW.md` を読むこと。** 正解は暫定で、まだ人の検品を通っていない。
未検品の正解で測った結果を、検品済みの結果と同じ顔で並べてはいけない。
